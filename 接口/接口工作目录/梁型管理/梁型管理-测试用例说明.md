## 三、请求头规范

所有梁型接口与通图号接口统一携带：

```json
{"Authorization": "${loginUserToken}", "Sys-dept-id": "${bfDeptId}"}
```

- `Authorization`：取自 `login.success` 提取的 `loginUserToken`（已带 `Bearer ` 前缀）
- `Sys-dept-id`：梁场机构 deptId，取自 `beamfield.dept.verify_f01` 提取的 `bfDeptId`（该值同时用于越权/缺省头的负向用例：缺失时只带 Authorization，伪造时用 `999999999`）

## 四、通图号 sjth 的取数方式

梁型的 `sjth` 就是通图号管理的 `bddId`，由系统自动生成，**不新建通图号**，直接查询取用：

```
GET /api/base/bfmBaseDesignDrawingsNumber/queryBfmBaseDesignDrawingsNumberVoList.ajax
```

对应测试数据 `beamtype.sjth.list`，按用途分 10 组提取——系统自带 10 条以上，一条通图号下挂一组梁型，比全部挤在同一条上更接近真实数据：

| 变量 | JSONPath | 使用的数据 |
| --- | --- | --- |
| `sjthA` | `$.data[0].bddId` | 基础新增组 A01~A05、判重/颜色/同名基线、SQL 注入数据 |
| `sjthB` | `$.data[1].bddId` | 「编辑-更换通图号」的目标值（U02 由 `sjthG` 改为 `sjthB`） |
| `sjthC` | `$.data[2].bddId` | **Q03 独占**，该通图号下只有 1 条梁型，供「按通图号查询」做精确断言 |
| `sjthD` | `$.data[3].bddId` | 列表查询组 Q01 / Q02 / Q05 |
| `sjthE` | `$.data[4].bddId` | 分页组 P01 / P02A / P02B / P03 |
| `sjthF` | `$.data[5].bddId` | 通过 id 查询 G01 |
| `sjthG` | `$.data[6].bddId` | 编辑组 U01~U07（U02 编辑时改为 `sjthB`） |
| `sjthH` | `$.data[7].bddId` | 通过 id 删除 D01~D03 |
| `sjthI` | `$.data[8].bddId` | 批量删除 B01~B05 |
| `sjthJ` | `$.data[9].bddId` | 模糊匹配 F01 / F02 |
| `sjthK` | `$.data[10].bddId` | **基础数据独占**（`基础梁型-*` 共 16 条），与功能用例造数隔离，执行完不清理 |
| `sjthDrawingA` / `sjthBeamCodeA` | `$.data[0].designDrawingsNumber` / `designBeamType` | 核对图号与梁型码，便于人工确认取数是否正确 |

前置判据是 `$.data` 长度 > 9（即至少 10 条）：数量不足时前置直接失败并给出明确提示，避免提取到空值后在用例里报出难以定位的错误。基础数据用例要取第 11 条，因此它的前置判据单独抬高为长度 > 10。

`sjthC` 是「按通图号查询」能做出强断言的前提——只有该通图号下独占一条记录，才敢断言返回 `length_eq 1`；否则按通图号查到一堆记录、只校验首条，等于没验证过滤是否生效。生成脚本内置两条自检：`sjthA`~`sjthK` 必须全部被使用；`sjthC` 只能被 Q03 使用。

> 编辑类报文（U01/U03/U04/U06/U07、主键不存在）的 `sjth` 与各自新增基线保持一致（`sjthG`），只有「更换通图号」用例刻意改为 `sjthB`——否则「sjth 保持不变」的全字段修改用例实际把通图号也改了。

## 五、基础数据准备（复用已有的 13 个数据键）

不重复造组织机构，直接复用测试数据表中已有的链路数据，并在**每条用例**的前置条件中做「存在性检查，不存在才新增」：

```
login.success                     → loginUserToken
dept.query.tree_success           → yunweiDeptId（运维单位）
beamfield.prep.detect_chain       → 查树判断梁场机构 TESTLC201 是否存在，同时提取 bfDeptId
   └ 不存在时依次执行：
       beamfield.prep.add_group           → 新增集团公司 G01（deptType=2）
       beamfield.prep.get_group_id        → 提取 groupId
       beamfield.prep.add_build_unit      → 建设单位 G02（deptType=3）
       beamfield.prep.get_build_unit_id   → 提取 buildUnitId
       beamfield.prep.add_proj            → 建设项目 G03（deptType=4）
       beamfield.prep.get_proj_id         → 提取 projId
       beamfield.prep.add_section         → 标段 G04（deptType=5）
       beamfield.prep.get_section_id      → 提取 sectionId
       beamfield.dept.create_f01          → 梁场 F01（deptType=6）
       beamfield.dept.verify_f01          → 提取 bfDeptId
beamfield.query.by_dept           → 查本梁场 bfmBeamField 记录（梁场基本信息）
   └ 查不到时执行：
       beamfield.prepare.add              → 以 deptId=${bfDeptId} 新增梁场基本信息
```

即：梁场机构与梁场基本信息都已存在时 0 次写操作；机构不存在时按 集团→建设单位→项目→标段→梁场 逐级补齐，基本信息缺失时再补一条。

这两类都属于**环境初始化数据**（组织机构链路、梁场基本信息），按清场规则不做删除，模块清场只清本模块产生的梁型记录。

## 七、基础数据（正交组合，供手工测试使用）

模块里另有一条**独立用例** `beamtype.base.seed`（子模块「基础数据」，`TC-BT-600`），它不是功能校验用例，只负责把一批梁型基础数据补进系统，供后续手工测试 / 其它测试直接使用。

**为什么单独成一条用例、且不与功能用例混用数据**：

| 隔离点 | 做法 | 原因 |
| --- | --- | --- |
| 名称前缀 | 统一 `基础梁型-` | 模块清场只删 `测试梁型-`，这批数据执行完会长期保留；反过来也不会被误认为功能用例造数 |
| 通图号 | 独占第 11 条 `${sjthK}` | 功能用例造数用 `sjthA`~`sjthJ`，两者七项判重组合天然不重叠，不会互相触发「梁型重复」 |
| 图例颜色 | 16 个全新色值 | 颜色全梁场唯一，必须避开功能用例已占用的 33 个色值，否则新增会被颜色重复校验拒绝 |
| 数据键 | `beamtype.base.*` | 与 `beamtype.add.*` / `beamtype.probe.*` / `beamtype.cleanup.*` 完全分开，便于单独维护 |
| 清场 | 不参与 | 基础数据是「要留下的」，模块清场只清 `测试梁型-*`；生成脚本有自检，防它被误纳入清场 |

## 八、数据隔离与清场策略

1. **造数放在前置、先查后建**：查询 / 分页 / 按 id 查询 / 编辑 / 删除 / 批量删除这几类用例，源数据都在**前置条件**里准备——先用探针（`beamtype.probe.<code>` 或 `beamtype.by_name.<code>`，按「名称 + 梁体类型 + 长度类型」定位）查一次，**查不到才新增，已存在就直接复用**；需要 `btId` 的，在探针查到后直接提取，若走了新增分支则新增后再查一次取主键（新增接口不返回主键）。这样即使库里已有同一条数据（上一轮残留、或环境本身预置），也不会因重复新增被判重拒绝而拖垮整条用例。
2. **用例之间无上下文依赖**：所有造数都在本条用例的前置里完成，可从任意一条用例开始执行，也可只跑某个子模块；`test_steps` 里只留被测请求与结果回查。
3. **模块级清场**：清场不单独成用例，而是挂在**模块最后一条用例**（`beamtype.delete.batch_no_auth`）的**后置步骤**中。后置步骤用一次列表查询（不带过滤条件）扫描本梁场全部梁型，逐个按名称判断是否存在，**存在才按 `btId` 删除**，共覆盖 47 个清场判据；即使该用例自身的测试步骤失败，后置清场仍会执行。该用例的 `order` 取模块内其余用例的最大值 + 1（本模块为 1），其余用例均为默认 0，保证它在模块内最后执行。
4. **清场名单覆盖「本应失败」的数据**：清场名单不再手写，而是从**所有新增/编辑报文**里自动收集 `测试梁型-` 开头的名称——既有正常造数，也有本该被拒绝的负向报文（缺通图号-A07、缺计划-A08、缺颜色-A09、**缺梁位-A10**、组合重复-A14、颜色重复-A15、未授权-A11 等）。这些数据「本不该存在」，但一旦系统放行就会变成遗留脏数据，因此与正常造数同等对待：**扫到了就删**。其中「缺 name」的那条负向报文若被放行，记录没有名称可定位，改用该报文独有的图例颜色兜底扫描（每条负向报文的颜色互不相同）。生成脚本内置覆盖自检：任一报文名称没有清场项、或无名称报文缺少颜色兜底，直接报错。
5. **只清自己的数据**：只删除名称以 `测试梁型-` 开头的记录（颜色兜底也只匹配负向报文专用的独有色值），不动组织机构、通图号、梁场基本信息，也不影响他人数据；删除动作幂等，重复执行无副作用。`测试梁型-` 前缀同时也保证数据可辨识：形如 `测试梁型-32m双线箱梁-A01`、`测试梁型-24m单线T梁-B02`，一眼可辨认且符合真实命名规律。
6. **断言优先 JSONPath**：状态码、枚举值、数值、字段集合等确定性内容全部用普通断言；只有提示语文案、`sjth` 业务语义、越权行为等不确定项才用 AI 断言。期望值需要用运行时的上下文变量时（如通图号 `sjthC`、主键 `btId`），在 `AssertionRule` 上写 `"ctx": {"is_ctx_var": true}`、`expect_value` 只填键名（不带 `${}`），执行器会在派发操作符前自动替换成上下文实际值——因此 `eq`、`contains`、`gt` 等任意操作符都适用。本模块的「按通图号过滤」「按 id 查询」就是用这种方式与前置提取的通图号比对（`sjthC` / `sjthF`），不再依赖测试步骤里是否存在新增报文。
7. **请求级去重**：同一「接口 + 请求头 + 请求体 + 查询参数」只保留一条 `api_test_data`。此前把 8 条「按名称回查」重复数据合并为统一键 `beamtype.by_name.<code>`——新增后用它提取 `btId`，删除/批量删除后用它断言记录是否已不存在（提取用 `jsonpath`，查不到记录时该库返回 `False`、提取自动跳过，不会因空结果报错）。仅两处有意保留同请求：`beamtype.query.list.all` 与 `beamtype.cleanup.scan_all`（前者断言字段完整性，后者提取 47 个 `btId` 供清场，提取内容不同）、`beamtype.delete.d03.first` / `beamtype.delete.d03.second`（幂等性用例本身要求同一请求连发两次）。生成脚本已内置该检查，重复即报错。
8. **落库状态唯一（判重/颜色）**：模块是按顺序执行的，新增成功的记录会一直留到终局清场才删除，所以「同时存在」的两条记录不能撞七项要素、也不能撞图例颜色。生成脚本改为**数据驱动**校验：从用例里挑出断言 `status=1` 的新增/编辑步骤，新增记为落地、编辑按原地替换处理（编辑后旧状态消失），负向报文只做单向冲突检查；**前置里「先查后建」的造数同样计入落地状态**（执行前会被确保存在），但不参与「同一份数据不得被两条用例执行」的检查——多条用例共用一条前置造数是安全的，第二条查到已存在就跳过新增。判重用例本身要求的「刻意重复」（A14 撞 A05 组合、A15 撞 A16 颜色）白名单放行。

| 9 | 架设图例颜色 | **全梁场唯一**：同一颜色不能被任何梁型占用，跨梁体类型也不行 | `beamtype.add.dup_color`：A16 为箱梁（#8B0000），A15 为 T 梁、七项要素全不同但颜色相同，断言失败 + 未落库（刻意跨梁体类型，可区分「全梁场唯一」与「同类型内唯一」） |
| 10 | 梁型名称 | **没有**重复校验 | `beamtype.add.same_name`：同名 A17 两条，七项要素与颜色都不同，断言新增成功且按名称查到 2 条 |
| 11 | `beamTypeColor` | **必填**（架设图例颜色不能缺席），同时又受全梁场唯一约束 | `beamtype.add.required_only` 回查 `beamTypeColor` 落库；`beamtype.add.miss_color`：不传该字段断言失败且未落库 |
| 12 | `beamLocation` | **条件必填**：T 梁（`beamBodyType=1`）必填，箱梁（`beamBodyType=2`）可不传 | `beamtype.add.required_only`（箱梁不传）断言新增成功；`beamtype.add.miss_location_tbeam`（T梁不传）断言失败且未落库 |
| 13 | 编辑报文的主键 | `btId` 为**请求体必填字段**（接口文档 Body 表明确「必须」），少了它无法定位记录 | 7 条编辑数据全部带 `btId`（3 条成功用例取 `${btIdU01~U03}`，2 条越权用例取 `${btIdU06}` / `${btIdU07}`，缺 name 用例取 `${btIdU04}`，主键不存在用例写 `not_exist_bt_id_99999`） |

## 十二、仍需留意

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | 分页参数非法（pageNum=0、pageSize=-1） | 后端会回退默认值还是返回参数校验提示尚未确认；用例只断言 `code=200` 且不 500，首次执行后可据实收紧 |
| 2 | 按 id 查询 / 编辑不存在的 btId | 二者未在本次确认范围内；用例仍断言「`code=200` 且不得 500」，若实际返回成功可改为与删除一致的强断言 |
| 3 | 模糊匹配下的排序 | 不同关键字可能命中多条，用例统一用 `data[0]` + 名称断言，若后端排序规则变化需同步调整 |
| 4 | 真实数据占用颜色/组合 | 颜色唯一性为**全梁场唯一**，判重按七项要素。若库里已有真实梁型占用了某个颜色或七项要素组合，对应新增会被拒绝。本套造数的 49 条落地记录（含 16 条长期保留的基础数据）使用互不相同的组合与冷门色值，执行前仍建议确认库内无同组合/同色记录 |
| 5 | 校验顺序（必填 vs 判重） | 后端先校验必填还是先判重未确认。缺参用例（425~427）已改用独立组合与独立颜色，两种顺序下提示语都应是必填缺失；若实际返回「梁型重复」，说明判重先执行，需同步调整 AI 断言 |
| 6 | `sjthC` 被真实数据占用 | 「按通图号查询」断言 `length_eq 1` 的前提是第 3 条通图号下只有 Q03 一条。这是**造数层面的独占**：若测试梁场已有引用该通图号的真实梁型，会返回多条导致失败。届时把提取索引换成一条未被占用的通图号（如 `$.data[n]` + 同步改 `sjthC`）即可，无需改断言 |
| 7 | 探针的定位精度 | 「先查后建」按「名称 + 梁体类型 + 长度类型」判断该条造数是否已存在。若库里恰有同名、同梁体类型、同长度类型但其他要素不同的记录（非本套造数产生），探针会判为「已存在」而跳过新增，后续断言可能与预期不符。届时换一个造数名称即可；正常清场后不会出现该情况 |
| 8 | 基础数据依赖第 11 条通图号 | `beamtype.base.seed` 用 `${sjthK}`（`$.data[10].bddId`）。系统若只有 10 条通图号，该用例前置会因 `$.data` 长度不足 11 而失败（其余 48 条用例不受影响）。届时去通图号管理补一条，或把提取索引换成别的未占用通图号并同步改数据 |
| 9 | 基础数据与功能用例共存 | 基础数据长期留在库里，功能用例每次跑都会重建自己的 `测试梁型-*` 并清场。两边靠「通图号不同 + 颜色不同 + 七项要素不同」保证互不干扰（生成脚本有全量自检）；若手工改过某条基础数据的通图号或颜色，需重新跑一遍生成脚本自检 |
